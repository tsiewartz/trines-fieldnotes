Integration reference

Power BI with Snowflake as the data platform

Snowflake holds and prepares the source data; Power BI provides reporting. Choose how reports access data, then where business definitions live. Import creates a reporting copy in Power BI; DirectQuery sends source SQL to Snowflake.

Documentation snapshot: 21 October 2026. No workload benchmarks; availability and compatibility require verification.

Decision guide

Choose a starting point

Follow the requirement that best matches your workload. These are evaluation paths, not guaranteed recommendations; data access and semantic ownership are separate decisions.

1. How should Power BI access the data?

  • Scheduled freshness is sufficient, and the model fits capacity

    Evaluate Import →

    Check refresh time and memory. Imported rows are stored in Power BI.

  • Cached summaries or history plus live detail are needed

    Evaluate composite / hybrid →

    Choose mixed tables or partitions to match the requirement; verify feature compatibility and query routing.

  • Source queries are needed for freshness or data volume

    Evaluate DirectQuery

    Then choose the Snowflake execution tier. Also assess this tier for the DirectQuery portion of mixed models.

    • Short, selective queries with high concurrency

      Benchmark interactive warehouses →

      Check the five-second limit, standard fallback, warm-up, and operating cost.

    • Longer, mixed, or not-yet-characterized queries

      Start with a standard warehouse →

      Establish a baseline using generated SQL and end-to-end report latency.

2. Where should business definitions live?

  • Reports depend on existing DAX behavior

    Keep the Microsoft semantic model →

    Snowflake supplies data and executes source SQL, not the Microsoft model's DAX.

  • Reports need selected Snowflake-defined metrics at a known grain

    Evaluate Semantic View SQL →

    Validate downstream aggregation; ratios and distinct counts are not generally additive.

  • Clients need live access to Snowflake semantics

    Evaluate the Snowflake XMLA endpoint →

    Availability, commercial terms, and calculation compatibility must be confirmed. GA status remains unconfirmed.

Model reuse is a separate track

Apache Ossie exchanges model metadata. It is not a query engine or an alternative to Import or DirectQuery. Validate converted definitions in the destination engine.

If requirements overlap, evaluate more than one path. Use the evaluation checklist to verify correctness, freshness, identity, latency, and cost.

01 / Data access & compute

Connection-pattern details

Choose a pattern to inspect its query path. Expand the implementation notes for constraints and checks.

Pattern details
Pattern 01 Established connector path

Import into Power BI

Power BI stores imported rows in its in-memory model and evaluates DAX there. Snowflake executes extraction queries when the model refreshes, not for each report interaction.

Snowflake Query at refresh time
→
Power BI model Imported data + DAX
→
Report visuals Served from memory
Typical use case

Daily management reporting or period-end analysis where scheduled refresh meets the freshness requirement and the model fits available capacity.

Technical trade-offs

A separate data copy, capacity memory, refresh duration, and handling historical corrections.

Implementation notes and constraints
Optimize the refresh path: use the current connector, select only required data, and verify that incremental-refresh filters reach Snowflake.
  • The ADBC-based Snowflake connector implementation 2.0 is generally available and the default for new connections.
  • Microsoft currently documents COUNT DISTINCT correctness and increased-memory-use issues in 2.0. Validate your deployed versions and important totals.
  • Interactive warehouses do not speed up visuals served entirely from imported data. Use a suitable warehouse for extraction.
  • Imported data is not re-authorized in Snowflake for every report viewer; design the Power BI access model deliberately.

Source: Microsoft Snowflake connector

Pattern 02 Established connector path

DirectQuery on a standard warehouse

Keep data in Snowflake. Power BI evaluates the report's semantic logic and sends generated SQL to Snowflake as needed.

Power BI report User interaction
→
Power BI model DAX to source SQL
→
Snowflake Standard warehouse
Typical use case

Operational reporting over changing source data, or detail-level exploration where importing the full dataset is impractical.

Technical trade-offs

Report-generated SQL, visual count, warehouse sizing, concurrency, and network latency.

Implementation notes and constraints
Freshness behavior: results are retrieved from the source when queried. Power BI caching and refresh behavior still affect what the user sees.
  • Measure end-to-end report latency, not just individual Snowflake query runtimes.
  • Test totals, high-cardinality filters, and complex DAX; one visual can issue multiple SQL queries.
  • Microsoft Entra ID per-user SSO is supported for DirectQuery when configured. Shared credentials are a different access pattern.
  • A warehouse change does not move the Power BI semantic model or automatically simplify DAX.

Source: Microsoft Snowflake connector

Pattern 03 GA · verify region

DirectQuery on an interactive warehouse

Power BI sends SQL through the Snowflake connector to an interactive warehouse. Power BI still owns the DAX model; only the Snowflake execution tier changes.

Power BI report Generated SQL via connector
→
Interactive warehouse Short, concurrent SQL queries
→
Existing tables No table copy required
Typical use case

Frequently used operational views with selective filters and many concurrent users, such as status by location or account-level drill-through.

Technical trade-offs

Warm-cache operation, a standard fallback warehouse, and workload-specific cost testing.

Five-second limit, fallback, cost, and availability
  • Queries have a five-second runtime limit. Longer queries are re-executed on a configured standard fallback warehouse, or fail if no fallback is configured. Existing standard tables are supported directly.
  • Resuming starts a one-hour minimum billing period. The minimum auto-suspend interval is 24 hours; manual suspension is possible.
  • Cold-cache performance differs from warm-cache performance. Region availability must be checked for the target account.
  • Complex joins, broad scans, or expensive distinct counts may be unsuitable. Benchmark your workload; no speedup is assumed.
  • This optimizes Snowflake execution, not Power BI rendering or visuals served from Import cache.

Source: Snowflake interactive analytics

Pattern 04 Feature / capacity dependent

Composite models & hybrid tables

A composite model combines storage modes or sources. A hybrid table combines Import and DirectQuery partitions within one table. Queries may use cached data, Snowflake, or both.

Power BI report Semantic model routes queries
→
Cached data Dimensions, history, or summaries
+
Snowflake detail DirectQuery when needed
Typical use case

Cached monthly summaries with live transaction drill-through, or imported historical partitions with a DirectQuery partition for recent changes.

Technical trade-offs

Storage-mode design, cache freshness, relationships, and consistent results across query paths.

Implementation notes and constraints
Two distinct patterns: composite models can use imported aggregations over DirectQuery detail; hybrid tables combine Import and DirectQuery partitions within a table.
  • Dual-mode dimensions can support both cached and source-side paths when used with facts from the same source.
  • Hybrid tables do not support aggregation tables over their individual DirectQuery partition. Do not assume every optimization can be combined.
  • Check licensing and capacity for the selected features, including real-time incremental refresh.
  • Test totals, relationships, access rules, and the consistency of cached and current data.

Source: Microsoft composite-model guidance

The interface returns rows, not a complete browsable Power BI semantic model. Validate filter context and downstream aggregation; do not sum ratios or precomputed distinct counts. This is not automatic Power BI model discovery.

Model reuse and cataloging

Apache Ossie (Incubating)

Use case: transfer model definitions between tools or maintain a common exchange representation. Formerly Open Semantic Interchange, Ossie has an initial bidirectional Power BI converter with TMDL integration. TMDL is Microsoft's Tabular Model Definition Language.

September 2026 announcement

DAX is a recognized expression language in the specification. That does not mean every DAX expression automatically becomes executable Snowflake SQL. Validate conversion coverage, results, and change ownership; do not assume lossless conversion or continuous synchronization.

Power BI model ingestion

Use case: initialize a Snowflake Semantic View from an existing Power BI model. Ingest a .pbit template or .pbix report to map Snowflake-backed tables, relationships, and supported calculations. A .pbit contains no embedded data rows.

Documented feature coverage

Calculation groups, several time-intelligence functions, selection-dependent expressions, and report-level measures are among the documented exclusions. Treat ingestion as a starting point, not a lossless migration.

Horizon Catalog metadata connections

Use case: find reports and models, trace dependencies, or assess the impact of source changes. Metadata connections collect supported Power BI metadata for discovery, documentation, and cross-platform lineage.

Horizon Catalog documentation — check account availability.

This helps teams understand and find assets. It is not a report-serving connection, and it does not automatically synchronize every measure or calculation across platforms.

Evaluation checklist

Test the selected pattern against explicit requirements. Separate report rendering, semantic-model evaluation, source query execution, and data synchronization when measuring results.

Workload and freshness

  • Record data volume, update frequency, filter selectivity, and concurrent users.
  • Set a maximum acceptable age of data; include Snowflake data processing, model refresh, and BI caching.
  • Include drill-through, totals, broad date ranges, and high-cardinality filters.

Execution and latency

  • Capture Power BI-generated SQL and distinguish source time from end-to-end visual time.
  • Measure p50 and p95 for single-user and concurrent workloads; document result-cache and warm-cache conditions.
  • For interactive warehouses, record fallback frequency and latency after resume.

Calculation equivalence

  • Compare totals, ratios, distinct counts, period comparisons, and filter-context behavior with a reference result.
  • For SQL consumption, record the output grain and which downstream aggregations remain valid.
  • For conversion, inventory unsupported DAX, calculation groups, relationships, and report-level measures.

Identity and operations

  • Identify the executing principal: report viewer, refresh identity, or shared connection identity.
  • Test access behavior separately for imported model data and Snowflake source queries.
  • Verify client and gateway versions, network requirements, region support, and preview eligibility.

Data movement and cost

  • Account for Power BI imports, Snowflake warehouse caches, model metadata, and refresh jobs.
  • Include Snowflake compute and storage, Power BI licensing/capacity, and relevant network charges.
  • Use a representative operating period; a single warm query does not establish total cost.

Model lifecycle

  • Assign ownership of source definitions and any generated or converted models.
  • Test schema changes, refresh failures, deployments, and rollback procedures.
  • Keep runtime connectivity, model conversion, and catalog metadata ingestion as separate validation tracks.

No single pattern is recommended for every workload. Document the measured results and any unsupported requirements before selecting an architecture.
