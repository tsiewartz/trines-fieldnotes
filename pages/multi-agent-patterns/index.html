Where do the prompts go?

Each agent makes its own decisions, so orchestration prompts are split across three layers.

1 · Main agent
Which domain?
  • orchestration: routing rules per domain, how to split cross-domain questions, when to ask the user
  • response: tone and format for the end user; merge specialist answers
2 · Sub-Agents MCP
Tool descriptions
  • The main agent picks a sub-agent from each CORTEX_AGENT_RUN tool's name and description
  • Keep them specific and consistent with the routing rules
3 · Each sub-agent
Which tool in the domain?
  • orchestration: when to use the semantic view, search or charts
  • response: factual, structured output — it is read by another agent

Business rules (definitions, filters) belong in the semantic view itself. With agent toolsets, only tools are inherited — all instructions must live in the main agent.

Pros

  • Cleanest separation of concerns
  • Each sub-agent can be tested independently
  • Sub-agents get data_to_chart (native tools)
  • Easy to add new domains — just add another sub-agent

Cons

  • Extra orchestration hop (main → sub = 2 LLM calls minimum)
  • Cross-domain questions require calling multiple sub-agents and merging results
  • More objects to manage (4 agents + 1 sub-agents MCP)
B
All tools in one agent

Where do the prompts go?

One agent makes every decision, so all orchestration lives in one spec — tool descriptions carry most of the weight.

1 · Orchestration
Which tool for which question?
  • One section per domain: which semantic view and search service to use
  • How to combine tools for cross-domain questions; when to chart or run code
2 · Tool descriptions
Disambiguate similar tools
  • Each semantic view and search tool needs a description that names its domain and what it does not cover
  • This matters more as the tool count grows
3 · Response
How to answer
  • response: tone, format and citations for the end user
  • One place to keep the experience consistent

Business rules (definitions, filters) belong in the semantic views. Keep the orchestration prompt structured by domain so it stays maintainable as it grows.

Pros

  • Simplest architecture (1 agent, 1–2 MCP servers)
  • No routing overhead — direct tool selection
  • Cross-domain questions handled naturally in one turn
  • Fewer LLM calls per question

Cons

  • Tool selection accuracy degrades with many tools (9+ can confuse the LLM)
  • One massive instruction prompt — harder to maintain
  • Cannot test domains independently
  • No modularity — adding a domain means editing the single agent

Where do the prompts go?

The main agent decides whether to answer directly or delegate, so the key prompt is the line between the two.

1 · Main agent
Answer or delegate?
  • orchestration: which questions to answer with its own tools, which to hand to a specialist
  • response: one voice for the user, whether answered directly or delegated
2 · MCP tool descriptions
Specialists and shared tools
  • Specialist Agents MCP: each CORTEX_AGENT_RUN description says which complex questions it owns
  • Utility MCP: search and SQL tools described so they don't overlap the specialists
3 · Each specialist
Multi-step reasoning in the domain
  • orchestration: how to break down domain questions across its semantic view, search and charts
  • response: factual, structured output for the main agent

Avoid overlap: if a question can be answered both by a main-agent tool and a specialist, the orchestration prompt must say which wins.

Pros

  • Best of both worlds: simple questions answered directly, complex ones delegated
  • Fewer LLM hops for common questions (handbook lookup, org chart)
  • Each tool uses the integration that fits it: native where you need native-only features (charting, analytical search), MCP where tools are shared across agents or call other agents
  • Complex domains stay modular — specialist agents can be built, tested and evolved independently

Cons

  • Most complex to design — must decide what lives where
  • Potential overlap in routing decisions
